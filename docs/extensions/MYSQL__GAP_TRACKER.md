#### 4.3.2 设计决定与已知差异

| 编号 | 项 | Rust 实现 | 与 Java 的差异 | 为何保留（收益/依据） |
|---|---|---|---|---|
| MYSQL-X01 | 键列 `COLLATE utf8mb4_bin` | `src/state/mod.rs:66-81`、`src/store/dialect.rs:99-117`、`src/snapshot/mod.rs:27-38` 三处 DDL 均只在**键列**钉 binary collation，payload 列沿用表默认 `utf8mb4_unicode_ci` | 与 Java `main`（#3288 / `2349533a1`）**一致**；相对「旧版 DDL（键列大小写不敏感）」是有意差异：不改则 `README.md`/`readme.md`、`alice`/`Alice` 在主键上互相覆盖 | 存量库需手工 `ALTER TABLE ... | MYSQL-X02 | 四个 backend trait 缝 + 同步/异步桥 | `StateBackend` / `SqlBackend` / `SnapshotBackend` / `LockBackend`（`src/state/mod.rs:100-256` 等），`MysqlAsyncBackend` 用一个 1-worker runtime `block_on` 驱动 async 驱动（`src/driver/real.rs:1-30`） | Java 组件直接拿 `DataSource` 每条语句 `getConnection()`；Rust 由 trait 注入，单测零网络 | 无 MySQL 服务器即可跑 108 个单测；驱动可替换（`mysql_async` / `jdbc_bridge`）；代价是同步缝需 `spawn_blocking`（guard 已做） |
| MYSQL-X03 | trait 签名无 `Result` 的写/读入口吞错 | `BaseStore::put/delete/get`、`AgentStateStore::save/delete/get` 失败返回 `()`/`None`（`src/store/mod.rs:191-247`、`src/state/mod.rs:512-596`），同时提供 `try_put`/`try_put_if_version`/`try_build`/`save_if_version` 等可报错入口 | Java `JdbcStore`/`MysqlAgentStateStore` 每个方法都 `throw RuntimeException` | 由 harness/core trait 签名决定，crate 内不能改；生产调用应走 `try_*`（尤其写路径），否则数据库故障会表现为「写入成功但无数据」 |
| MYSQL-X04 | 锁租约生命周期 | `MysqlLockLease` 实现 `Drop` 自动 `RELEASE_LOCK`，并按 lock name 记账；`is_held` 走 `SELECT IS_USED_LOCK(?)`（`src/guard/mod.rs:126-232`、`src/driver/real.rs:670-700`） | Java 只在 `SandboxLease.close()` 里 `RELEASE_LOCK` + `Connection#close()`；Java 接口无 `isHeld`/`activeCount` | 忘关租约也不会泄漏锁（Java 忘 close 会占着连接直到池超时）；`IS_USED_LOCK` 能看跨进程占用，Java 无此能力 |
| MYSQL-X05 | 同锁重复获取 | 本地已持有同名锁时直接返回成功，不再发 `GET_LOCK`（`src/driver/real.rs:600-612`） | Java 每 `tryEnter` 都新开连接发 `GET_LOCK`：同一会话可重入成功，但只 release 一次就会提前释放另一租约 | MySQL `GET_LOCK` 是会话级锁，重入语义会泄漏租约；本地 no-op 保证「一次获取一次释放」 |
| MYSQL-X06 | 列表全量重写策略 | `src/driver/real.rs:354-400`：先 UPSERT `from_index..len`，再 `DELETE ... item_index >= len`；`from_index == 0` 即全量覆写 | Java `deleteListItems`（全删）→ `insertAllItems`（批量 INSERT） | 崩溃窗口内不会出现「列表被删空」；写入量更小（只写变化尾巴）；索引空洞也能自愈（配合 MYSQL-07 修正后） |
| MYSQL-X07 | 构造默认值 | `MysqlAgentStateStore::new` 默认 `create_if_not_exist = true`（`src/state/mod.rs:288-296`），且不吞 bootstrap 错误 | Java 无参构造是 **verify-only**（`createIfNotExist = false`） | 保留 Rust 历史默认（上层 `MysqlDistributedStore::create` 在 Java 侧也是 `new MysqlAgentStateStore(ds, true)`）；需要 Java 无参语义时用 `with_config(.., false)` |
| MYSQL-X08 | CAS 更新语句形状 | `UPDATE ... SET version = version + 1 WHERE ... AND version = ?`（`src/driver/real.rs:297-333`） | Java `SET version = ?`（= `expectedVersion + 1`，`updateIfVersion`） | 等价且不依赖调用方传入的陈旧算术值；影响行数仍是 1/0 判定，原子性相同 |
| MYSQL-X09 | harness 装配 | `MysqlDistributedStore::to_harness_distributed_store()` 把四组件投影进 harness `DistributedStore`（`src/distributed_store.rs:151-170`） | Java `DistributedStore` 本身就是四方法接口，直接返回组件 | harness 的 `DistributedStore` 是字段型 composite；投影是唯一不改 harness 的接法（tracker §2.2 已裁定） |
| MYSQL-X10 | `jdbc_bridge` 门面 | `src/jdbc_bridge/*`（feature `jdbc-bridge`）：一行构建 `agentscope_extensions_jdbc::JdbcDistributedStore` + MySQL executor | Java 无此层；但 Java `MysqlDistributedStore` 已 `@Deprecated(forRemoval)`，官方替代正是 `JdbcDistributedStore` | Rust 把 workspace 拆成 mysql/jdbc 两个 crate，桥接避免调用方自己拼 executor+dialect；默认构建不引入 jdbc 依赖 |
| MYSQL-X11 | feature 门控与失败语义 | `default` 无驱动；`mysql_async` 开真驱动；未开时 `MysqlAsyncBackend::connect` 与 `MysqlJdbcStore::build` 返 `DriverUnavailable`（`src/driver/stub.rs`、`src/jdbc_bridge/stub.rs`） | Java 无 feature 概念，缺驱动是运行期 `ClassNotFoundException` | 默认构建零重依赖；且**失败前置到构造期**，不会出现「看似可用却静默丢写」的 store |

### 4.3 与 Java 的已知差异（有意为之，非缺口）

#### 4.3.1 设计决定（不迁移）

| 编号 | 项 | Java 参考 | 不迁移理由（源码级依据） | 影响面 |
|---|---|---|---|---|
| PG-D01 | Jackson `ObjectMapper` 可插拔注入 | `store/PostgresBaseStore.java#Builder.objectMapper`、`#serialize`/`#deserialize`（`ObjectMapper` 字段 + `TypeReference<Map<String,Object>>`） | Rust 固定 `serde_json`，`StoreValue = serde_json::Map<String, serde_json::Value>`（`store.rs:111-123` 的 `serialize`/`deserialize`），序列化器非可插拔、无注入点；`rg 'ObjectMapper'` 零命中（另核 `Serializer`/`ValueSerde` 亦零命中） | 自定义序列化（如自定义日期格式）无法在 store 层替换，需在调用方处理 |
| PG-D02 | `getDataSource()` / `close()` / `DataSource` 生命周期与池化归属 | `state/PostgresAgentStateStore.java:701`（getDataSource）、`:737`（close 空实现）、各 `dataSource.getConnection()` | Rust 无连接所有权：client 为 `Arc<dyn PostgresClient>` 由调用方持有（`state.rs:130-140`、`client.rs:182-217`），无 `close` 语义可迁；`rg 'fn close' src/state.rs` 零命中（另核 `Drop for PostgresAgentStateStore` 亦零命中） | 连接/池生命周期由宿主管理；空池问题见 PG-05 |
| PG-D03 | JDBC 检查异常体系（`SQLException`/`IllegalStateException`/`RuntimeException` 包装粒度） | `store/PostgresBaseStore.java`（`get/put/search/delete` 各抛 `IllegalStateException("PostgresBaseStore ... failed")`）、`state/...java`（各方法 `throw new RuntimeException("Failed to ...")`） | Rust 统一为 `error::PostgresError`（`Query`/`Schema`/`Decode`/`Encode`/`InvalidIdentifier`/`LockTimeout`/`DriverUnavailable`，`error.rs:8-34`）+ `From<PostgresError> for CoreError`；Java 的 message 逐字搬运无意义，语义按变体表达 | 错误分类比 Java 更细，但 `BaseStore`/`AgentStateStore` trait 无错误通道 → 见 PG-08 |
| PG-D04 | `executeInWriteTransactionKeepsAutoCommitWhenAlreadyDisabled` 的 autoCommit 复用语义 | `state/...java#executeInWriteTransaction:245-262`（保存/恢复 `conn.getAutoCommit()`） | Rust 写事务走**专用连接** `PostgresClient::execute_in_transaction`（`client.rs:200-217`、`driver.rs:165-176` 显式 `BEGIN`/`COMMIT`/`ROLLBACK`），不存在「连接已被外部关闭 autocommit」的复用状态；`rg 'auto_commit\|autocommit'` 零命中 | 无（语义更强：不依赖调用方连接状态） |
| PG-D05 | null 参数防御性校验（`Objects.requireNonNull`、`IllegalArgumentException("... must not be null")`） | `state/...java`（`rejectsNullDataSourceInConstructor`、`validateSessionId`）、`snapshot/...java#upload`（`requireNonNull(data)`）、`store/...java#namespacePath`（`segment must not be null`） | Rust 类型系统已排除：`Arc<dyn PostgresClient>`/`&str`/`&[u8]`/`&[String]` 不可为 null，`expected_version: u64` 排除负值（对应 Java `putIfVersionRejectsNegativeExpectedVersion`，`store.rs:182-186`）；Rust 侧 null 只能显式构造（`SqlValue::Null` / `Cell::Null` 枚举变体，`client.rs:20-27,63-70`），不存在隐式 null 实参 | 无（用编译期替代运行期校验） |
| PG-D06 | 测试栈 H2 + Mockito + JUnit5（含 `ResultSet#close` 失败、`SQLException` 包装细节用例） | `src/test/java/.../{PostgresBaseStoreTest, PostgresAgentStateStoreTest, PostgresSandboxExecutionGuardTest, PostgresRemoteSnapshotClientTest, PostgresDistributedStoreTest}.java` | Rust 无 mock 框架与 JDBC 资源对象：以 `MemoryClient`（内存 SQL 模拟器）+ trait fake（`FailingClient` / `BatchOkQueryFailClient` / `TruncateFailClient` / `DdlFailClient`）等价覆盖；`ResultSet#close`/`Connection#close` 失败在 seam 上不可表达 | 覆盖等价，但方法级 1:1 溯源率非 100%（见 PG-06） |

#### 4.3.2 设计决定与已知差异

| 编号 | 项 | Rust 实现 | 与 Java 的差异 | 为何保留（收益/依据） |
|---|---|---|---|---|
| PG-X01 | 锁 key 哈希算法 | 自实现 `murmur3.rs`（MurmurHash3 x64_128 + seed 104729，`lock_key` 取 `h1`），金标向量钉住 | Java 依赖 `org.apache.commons.codec.digest.MurmurHash3`；Rust 零第三方依赖 | 输出与 Commons Codec 逐字节一致（`murmur3.rs:195-250` 金标向量），跨语言 advisory lock key 互通；避免为一个哈希引入 commons-codec 等价依赖 |
| PG-X02 | 专用锁会话抽象 | `PostgresClient::open_lock_session -> Box<dyn PostgresLockSession>`，默认实现返回 `DriverUnavailable`（`client.rs:195-200`），`PgSimpleClient` 每租约新建连接（`driver.rs:156-163`） | Java `dataSource.getConnection()` 每租约一条连接并 `close()` | 显式建模 PG 会话级锁；不支持专用会话的客户端**拒绝**而不是假装加锁（早期共享单 client 会让同进程两个租约互相「加锁成功」） |
| PG-X03 | 写事务能力缝 | `execute_in_transaction(&[SqlStatement]) -> PgResult<Vec<QueryOutcome>>`（batch 形式），默认实现报错（`client.rs:200-217`） | Java `executeInWriteTransaction(Connection, SqlOperation)` 用闭包 | 闭包参数会破坏 trait 对象安全并引入 async 生命周期问题；batch 形式等价且可被测（`MemoryClient` 仿真回滚） |
| PG-X04 | 分布式组合与护栏抽象 | `distributed_store()` 用 harness `DistributedStore::builder()` 填 5 槽（`distributed.rs:74-98`）；`impl SandboxGuard for PostgresSandboxExecutionGuard`（`guard.rs:223-309`） | Java `implements DistributedStore`（4 个方法）+ `implements SandboxExecutionGuard` 接口 | Rust harness 的 `SandboxExecutionGuard` 是具体 struct，故走 2026-10-28 新增的 `SandboxGuard` trait + 组合槽；降级语义问题见 PG-04 |
| PG-X05 | `put_if_version` 失败表达 | 返回 `bool`（CAS 失败=false，SQL 故障亦=false + warn，`store.rs:182-248`） | Java：CAS 失败返回 false，**其它 SQLException 抛 `IllegalStateException`** | harness `BaseStore::put_if_version` 签名为 `-> bool`，无错误通道；记为差异并见 PG-08（补 warn） |
| PG-X06 | async/同步桥接 | async trait 经 `tokio::task::spawn_blocking`（`blocking.rs:15-33`、`state.rs:169-188`） | Java 直接在调用线程上阻塞 JDBC | 避免阻塞 Tokio worker；同步 `BaseStore` 侧缺同类保护见 PG-01 |
| PG-X07 | 锁轮询间隔与超时精度 | `sleep(20ms)`，`lock_timeout: Duration` 原样保留（`guard.rs:140-183`） | Java `Thread.sleep(100ms)`，`Duration#toSeconds()` 截断为 `int` | 更细的退避粒度、亚秒超时可用；对外语义（超时报 `LockTimeout`）一致 |
| PG-X08 | 标识符校验覆盖范围 | 快照表名也走 `sql::validate_identifier`（`snapshot.rs:48`） | Java `PostgresRemoteSnapshotClient` 直接拼 `tableName`，**不校验** | 防 SQL 注入（表名无法参数化）；不影响合法用法 |
| PG-X09 | `sub_key` 不参与锁 key 派生 | `compose_lock_key` 只用 `scope`+`value`（`guard.rs:122-131`） | Java `SandboxIsolationKey` 无 `sub_key` 字段（`harness/agent/sandbox/SandboxIsolationKey.java:35-38` 仅 scope+value） | 保持跨语言 key 互通；代价是仅 `sub_key` 不同的两个 key 会过度串行（安全侧，不会破坏互斥） |
| PG-X10 | 版本化 API 形态 | trait `get_versioned`/`save_if_version`/`supports_versioning` 全部覆写（`state.rs:650-716`）+ 固有 `save_versioned`/`version_of`/`save_if_version`（`state.rs:336-445`） | Java 只有接口方法（`supportsVersioning`/`getVersioned`/`saveIfVersion`），无同步固有形态 | core trait 上提版本化面（A2）后二者并存：trait 供 harness 调用，固有方法供 crate 内部与需要 `PgResult` 的调用方；语义一致（均有测试钉住） |
| PG-X11 | 快照 spec 形态 | `PostgresSnapshotSpec(RemoteSnapshotSpec)` newtype + `postgres_snapshot_spec()` / `_with_table()` 辅助函数（`snapshot.rs:133-185`） | Java `PostgresSnapshotSpec extends RemoteSnapshotSpec` + 2 个构造器 | Rust 组合优于继承，且便于同时暴露 spec 与 helper；`impl SandboxSnapshotSpec` 委托（`snapshot.rs:154-185`） |
